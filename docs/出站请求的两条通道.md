# 出站请求的两条通道（2026-10-21）

这天报了三个「看不了」，查下来是两类病：两个是同一个结构缺陷的两次抽样，一个是配置和站点的漂移。写完免得下次重走。

---

## 一、三个故障，一条线

| 报告 | 症状 | 根因 |
|---|---|---|
| AGE 动漫一集都看不了 | 分集全部播不出 | 2.0.16 让播放列表绕中继后，中继把该直连的 CDN 塞回代理，CDN 按地区 403 |
| Pornhub 看不了 | 列表出、点开转圈 | 中继没套源声明的 Referer/UA，分片一律 403 |
| mrds66 封面全空 | 封面格一片灰 | 站点把图床从 `pic.jtzatly.cn` 换到 `pic.sugfew.cn`，配置白名单没跟 |

前两个是同一件事：**这个 App 有两条出站通道，各自判一遍「带什么头、走不走代理」**。

- `AiiHttp`（接口 / 封面 / spider 的 net）吃完整的源声明：hosts、origin、headers 模板、路由表；
- `VlcRelay`（播放取流）是后长出来的：靠 `wrap()` 现判一次路由，请求头只转 VLC 递的那几个 —— 而 VLC 的 UA 是它自己的名字，Referer 一个不带。

规范文档里写着「`headers` 是 App 侧（封面、**播放取流**）发的请求头」。这句话没有被任何东西强制，实现里只有封面接了。文档描述的是一个不存在的统一层。

---

## 二、AGE：绕中继 ≠ 走代理

### 取证

2.0.16 的改动是把播放列表改成「一律绕中继」——要拿列表才能剔广告、才能改写相对地址。但中继里的 OkHttp 仍然无条件跟随 `effectiveProxy()`。

AGE 的 ffm3u8 线路解出 `vip.ffzy-plays.com`，而 `DirectHosts` 里明明白白写着它该直连（樱花同款采集站 CDN）。走代理出去是境外 IP：

```
403 Forbidden
The region has been denied.
Connection: 64.64.224.121 (Client)
```

一个源的所有集一起挂，因为所有集都在这些 CDN 上。

`VlcRelay.wrap()` 的注释自己就写过这个坑：「relayClient 如果不摘代理，反而把直连域名又塞回那条节点，表就白挂了」。改前靠 `wrap()` 里 `mustProxy` 那道闸拦住；播放列表绕开闸之后，闸就形同虚设。

### 修法（2.0.17）

`MediaProxy.relayClient(boolean viaProxy)` 拆两份 client，`VlcRelay` 用 `relayViaProxy(url)` 按 `NetRoute.mustProxy` 算。

### 一个必须说清的边界

AGE 站点自己也在大面积失效。《潮与虎》第 1 集在 AGE 官网上直接显示「视频加载失败，请稍后再试」，解析站的回答是 `Code=9`。抽样首页 10 部：**7 部 Code=9、3 部 Code=10**。

`Code=9` 不是我们的 bug，是「这一集的资源在源站已经抓不到」。App 能做的是把话说清楚，不是把它修好。

## 三、Pornhub：绕中继 ≠ 带对头

### 取证

真机日志三段，一眼看出坏在哪一层：

```
上游 200  master.m3u8
上游 200  index-v1-a1.m3u8
上游 403  seg-1-v1-a1.ts
```

列表进得来、分片全被挡 —— 不是解析链路，是取流被 CDN 的防盗链拒了。phncdn 的 HLS 只认站点 Referer：m3u8 放行，ts 一律拒。

### 修法（2.0.18）

播放器打开时把 `SiteProfile.current(this)` 交给 `VlcRelay.setSourceProfile`，中继转发时套用源配置里那份 `headers` 模板：`{origin}` 换源域名，换完是空串或光一个 `/` 的头不发（缺 Referer 是 200，发个错的反而 403），同名头覆盖 VLC 那份 —— 源写的才是权威。

真机验证（同一台、同一个代理）：修前 `seg-1/3/5` 全 403，修后全 200，VLC 正常解 TS 出画面。

## 四、收进一个装配点（2.0.19）

两件判断各收成一份实现，放在 `Outbound`：

```java
Outbound.applyHeaders(builder, profile, url)   // 源模板，{origin} 换源域名
Outbound.viaProxy(url)                         // NetRoute.mustProxy 一个判据
```

`AiiHttp` 里那份一千多字节的模板实现整段搬过去，`VlcRelay` 的两个方法变成一行委托。

顺手改了 `originOf` 的兜底：原来解析不出来返回原 URL，会让 `{origin}/` 拼成垃圾 Referer 发出去；现在返回空串，走「空串就不发」那条。只影响异常路径。

### 以后加通道的规矩

新加任何一种出站请求（字幕、解密密钥、封面兜底），先去 `Outbound` 确认一次判据，别各自抄。绕开它得先把 `OutboundTest` 那 7 条用例删掉 —— 用例存在的意义就是这个。

### 为什么这不是「再补一个 if」

补两次 `if` 只会等来第三次。真正的问题是**声明式配置缺强制入口**：壳不认识任何站点，所有站点知识都在配置里；每多一个消费方（接口、封面、播放、字幕、密钥），就要重新读一遍契约，而没有任何东西强制它读全。

## 五、mrds66：另一类漂移

这个跟壳无关，是配置和站点之间的漂移。

站点把图床从 `pic.jtzatly.cn` 换成了 `pic.sugfew.cn`（首页 44 张封面全在新域），而 `/srv/cfg/spiders/mrds66.json` 的 `cover.allowedHosts` 还停在旧域。客户端的封面加载器只允许拉白名单里的域（这是安全边界：免得一个坏源把 App 变成任意地址的图片代理），于是每张封面都撞「无效封面域名」。

加密参数没变 —— 拿配置里的 key/iv 去解 sugfew 的图，出来是 1300×640 的 JPEG。

修法：`allowedHosts` 两个域都留（新文章在新域，历史文章还有挂在旧域的），`mrds66.js` 的 `hosts` 一并补上。

### 这类问题会反复遇到

**白名单写在配置里、配置要重装源才更新**。站点换 CDN 是常事，每换一次就得有人改配置、用户再重装一次源，中间那段时间封面全空。

> **（2026-10-31 更新）这一类已经由封面信任模型根治**：新客户端对名单外的封面主机自动裸拉试一次，验图通过就进观测集，图床轮换不再需要改配置、重装源——本节描述的「中间那段时间封面全空」在 ≥ 2.0.29 上不再成立（45 秒内的灰块是网络冻结，会自愈）。安全边界没有松：非 https / 字面 IP / 内网 / `.local` 的硬地板任何档位都拦。机制与取舍见[封面信任模型改造方案](history/2026-10-31-封面信任模型改造方案.md)。下面这条「兜底」因此不需要做了。

壳这边能做的兜底：把 spider 自己声明的 `hosts` 也当封面白名单（现在校验只认 `cover.allowedHosts`）。代价是放宽取图边界 —— 要不要加，是个产品决定，不是技术决定。

## 七、下次遇到「某源看不了」的判据

按这个顺序查，别跳：

1. **接口通不通** —— `[http] GET …` 有没有回 200。接口挂了是源的问题。
2. **解析出没出直链** —— 日志里 `解出地址` 那行。出不来，看是站点改版还是第三方解析站（AGE 那种）在拒。
3. **列表拿没拿到** —— `上游 200 master.m3u8` / `播放列表改写 N 条`。
4. **分片通不通** —— `上游 20x seg-*.ts`。403 先怀疑请求头（Referer/UA），410 是资源没了，`经代理/直连` 那两个字直接告诉你走的哪条出口。
5. **只有封面坏** —— 先过 45 秒再刷一次（≥ 2.0.29 名单外主机会自动裸拉自愈），仍灰再查站点图床域名对 `cover.allowedHosts`。
