## 发版清单（2026-10-18 更新）

```bash
cd work/android
./gradlew clean :app:testDebugUnitTest :app:assembleRelease
```

产物在 `app/build/outputs/apk/release/app-arm64-v8a-release.apk`，2026-10-31 的 2.0.28 实测 39.1 MB
（`extractNativeLibs` 打开后的体积；关掉会变成约 70 MB）。

发版：

```bash
APK=app/build/outputs/apk/release/app-arm64-v8a-release.apk
cp "$APK" /tmp/AIIvideo-v<版本>-release.apk
shasum -a 256 /tmp/AIIvideo-v<版本>-release.apk

gh release create v<版本> /tmp/AIIvideo-v<版本>-release.apk \
  --title "AIIvideo <版本>" --notes-file notes.md --latest
```

然后**必须**更新仓库根目录的 `android-update.json` 并 push —— 客户端的
`UPDATE_MANIFEST` 就是从这个文件读的，不更新的话所有人永远看到上一版：

（下面这段是格式样例，版本号停在 1.0.24 没跟着改 —— 字段和硬校验才是要看的东西。
每次发版实际写什么，看仓库根目录那份 `android-update.json`。）

```json
{
  "versionName": "1.0.24",
  "tag": "v1.0.24",
  "versionCode": 10024,
  "apk": "AIIvideo-v1.0.24-release.apk",
  "urls": [
    "https://gh-proxy.com/https://github.com/zhaoruizhe81/AIIvideo/releases/download/v1.0.24/AIIvideo-v1.0.24-release.apk",
    "https://ghfile.geekertao.top/<同上>",
    "https://gh.dpik.top/<同上>",
    "https://github.com/zhaoruizhe81/AIIvideo/releases/download/v1.0.24/AIIvideo-v1.0.24-release.apk"
  ],
  "sha256": "<64 位十六进制>",
  "size": 48946739,
  "notes": "一句话说明"
}
```

字段有硬校验（`UpdateManager.candidateFrom`）：`versionName` 必须 `x.y.z`、
`tag` 必须是 `"v" + versionName`、APK 名必须是 `AIIvideo-v<版本>-release.apk`、
`sha256` 必须 64 位十六进制、`size` 必须大于 0。任何一条对不上整份清单作废。

Release 资产里也传一份 `android-update.json`（`gh release upload ... --clobber`），
和仓库里那份保持一致 —— 历史上两条路都有客户端在读。

**仓库里不放 APK。** 二进制进了 git 历史就删不掉；APK 里烧着账号服务器的
实际地址和 appId，放 Releases 至少是个显式动作。

**没有 CI。** 构建需要原始样本 APK 和签名密钥，都不是这个仓库的东西。

## 内置播放器（libVLC）

**2026-10-17 起全应用只用内置播放器。** 网页 `<video>` 那条路已经移除，不是开关关掉——
`feedPlayer.open()` 直接解析地址、把 `{eps,index,url}` 递给 `VlcPlayerActivity`，页面这边
只剩一屏「正在打开播放器…」。竖滑切集、左右滑拖进度、单击出控件、倍速面板全在 Activity 里，
WebView 里不再套第二层。退出播放器后 `hgResume` 读 `__player:last` 收进度，然后落回详情页
（原来落回 feed 页，那页没了）。

`feed-player.js` 里 `render()/attach()/bindVideo()` 保留着但**已经没有任何调用点**——
将来要恢复网页兜底时是现成的，别当成活代码读。

1.0.18 起，APK 里带了一个原生播放器 `VlcPlayerActivity`，用 libVLC 3.7.7。目的只有一个：WebView 的 `<video>` 用哪个解码器由系统 WebView 决定，页面拿不到任何旋钮，于是同一部片在 A 机能放、B 机 `MediaError 4`（SRC_NOT_SUPPORTED）。libVLC 自带 FFmpeg，HEVC、10bit、AV1、AC3/E-AC3 都能软解，和设备硬解能力脱钩。

**这是全项目唯一进 APK 的原生依赖**，其余一切是 Gradle 工程里的普通 Java 源码（`app/src/main/java/`）：

| 部件 | 位置 | 说明 |
|---|---|---|
| Java 绑定 | `org.videolan.android:libvlc-all:3.7.7` | Gradle 直接依赖，dex 合并进 classes.dex（约 1250 个方法） |
| so | `jni/arm64-v8a/{libvlc,libvlcjni,libc++_shared}.so` | 45MB + 95KB + 9MB，只打 arm64 |
| 播放页 · 编排 | `VlcPlayerActivity.java`（1644 行） | 生命周期、翻页器、libVLC 起停、预取、进度落盘 |
| 播放页 · 控件 | `VlcControlsView.java`（528 行） | 整屏控件 + 自制控件（IconButton / SeekBar / scrim / 倍速面板），只认一个 `Host` 接口 |
| 播放页 · 状态 | `VlcSession.java`（152 行） | 地址缓存、解析令牌、失败标记、player↔地址、换线游标、续播现场 |
| 桥 | `__player:native` / `__player:last` / `__player:capability` | 独立的 `player` 前缀（不再是 detail 的一条隧道） |

播放页 2026-10-18 拆过一次，判断标准是「这块能不能单独测 / 单独读」：控件自带一套 mini UI 框架，状态是一堆生命周期各异的集合，两样都不该和 libVLC 起停搅在一起。`VlcSession` 的规则有单测（`VlcSessionTest`），因为「滑回失败过的页要重新给机会」这类规则在真机上根本没法稳定复现。

体积是这条路线的固定成本：**APK 从 8MB 涨到 26.2MB**。只打 `arm64-v8a`；32 位机器上 `LibVLC.loadLibraries()` 直接抛，`available()` 返回 false，页面退回网页播放器，不闪退。

### so 打包方式：extractNativeLibs / useLegacyPackaging

这两个开关必须**成对**设成一样的值（manifest 的 `android:extractNativeLibs` 和 Gradle 的 `packaging.jniLibs.useLegacyPackaging`），不一致时 Gradle 只给一句警告，行为未定义。

| 配置 | 下载体积 | 装完占磁盘 | 冷启动（真机 5 次） |
|---|---|---|---|
| `false`（1.0.23 及以前） | 56.0 MB | 58.7 MB | 341 / 348 / 365 / 397 / 414 ms |
| `true` （1.0.24 起） | **26.2 MB** | 81.5 MB | 311 / 349 / 359 / 360 / 400 ms |

差 30MB 全部来自 `libvlc.so`：它不压缩时 43.75MB，deflate 后 20.73MB。`false` 要求 so 强制 Stored（APK 里一个字节都不能省），`true` 才允许压缩、安装时再解压。

**换 true 的动机只有一个：下载体积。** 这个 App 走 GitHub Releases 分发，用户在手机流量下下载，30MB 是实打实的。代价是多占 23MB 磁盘（1.39 倍，不是两倍）。

**启动速度量不出差异，这一点反直觉但好解释**：两种配置运行时都靠 mmap，没有谁把 45MB 整份读进内存。`false` 是链接器直接 mmap APK 内的 Stored 条目，`true` 是安装时解压成实体文件后 mmap 那个文件。唯一多出来的是安装那一下的 1 秒解压。

> 实测环境：23113RKC6C / Android 16 / arm64-v8a。换机型要重量，尤其低端机和 eMMC 存储。

### 三个非显然的坑

**① 不能靠 `nativeLibraryDir` 判断 so 在不在。** 那个目录的内容取决于 `extractNativeLibs`：`false` 时 so 留在 APK 里由链接器 mmap，目录永远是空的；`true` 时安装时解压，目录里才有实体文件。也就是说「目录非空」只在某一种配置下成立，换个配置就静默判错。唯一的判据是「试着加载一次」：`LibVLC.loadLibraries()` 成功即可用，结果缓存在静态字段里（45MB 的映射，别反复试）。

**② `IVLCVout.setWindowSize()` 不调，画面会缩在左下角。** 不设窗口尺寸时 `android_window` 按视频原始分辨率（比如 320×192）铺在原点。要在 `surfaceChanged` 和 `onConfigurationChanged` 里把 SurfaceView 的像素尺寸喂给它。踩到时表现为「有声音、右下角一小块画面」，很容易误判成解码失败。

**③ 进度回传不要用 `startActivityForResult`。** `MainActivity.onActivityResult` 在 smali 的 dispatch 区里，动它风险不成比例。做法是：退出时把 `{id, episode, position, duration, finished}` 写进 `SharedPreferences(hg_player/last)`，页面回到前台读 `__player:last` 取走（读即清）。"回到前台"认 `window.hgResume`（原生 `onResume` 里有 `evaluateJavascript("window.hgResume && window.hgResume()")`），**不能只听 `visibilitychange`**——WebView 被 Activity 盖住时 `document.hidden` 经常一直是 false，那条事件根本不发。

顺带一个细节：`onPause` 和 `onDestroy` 都会落盘，两次都写的话页面收走第一条、prefs 里还剩一条一模一样的，下次回前台会把更新的进度盖回旧的。所以 1.5 秒内不重复写。

### 怎么验

真机上最快的一条：`adb reverse tcp:8000 tcp:8000`，本地 `python3 -m http.server` 起一个 HEVC 的 HLS 目录（`ffmpeg -i in.mp4 -c copy -f hls ...`），然后从播放页点「内置」。本机验证过的结果：`1896×1064 H264`、`720×1280 HEVC (H.265)` 都能满屏播，进度写回 `hgpref:progress`，`__player:last` 取到 `{position, duration}`。

### 排查时先记住的八条

这些是 2026-10-18~19 那一轮里代价最高的几条，现在仍然是规矩：

1. **判「没画面」不能只看截图。** `screencap` 连着三张纯黑也可能正在解码，先看
   `VideoFrameStats`（`enqueued` / `acquired` 是否在涨）和 `AudioTrack`，再用
   `screenrecord` 抽帧。设备自己锁屏时 `screencap` 也是纯黑、`input swipe` 不动 ——
   那不是代码问题。
2. **同一件事不许有两个读取点。** 「路由表说走代理、建客户端读全局设置」这类
   bug 修了三次才干净；现在路由只在 `NetRoute`、代理串只在 `ProxyRoute`、
   请求头只在 `Outbound`。
3. **桥的入参只 stringify 一次。** 驱动脚本 `JSON.stringify` 之后 `call` 内部又编了
   一遍，Java 收到的是字符串字面量 —— 表现为每次都超时，不报错。
4. **数组长度会变，游标不会。** 换线时过滤掉「当前这条」，数组缩水而游标照走，
   第二条备选永远试不到。
5. **删代码按方法头取块，别靠缩进猜。** 一次贪心切片把相邻方法一起删了，
   报错全指向别处。
6. **扫源码里的标记要跳过注释和字符串。** `indexOf('__spiderSite')` 命中的是注释里
   的同名提及，接着找到的 `{` 是别的函数体。
7. **核心的能力要按二进制验，不能按配置字段假设。** `app/libs/libv2ray.aar` 里是
   **v2fly 的 v2ray-core v5**，不是 Xray —— REALITY 是 Xray 独有协议。配置里写
   `"security":"reality"`，v2ray 不认识，**静默按 `none` 处理**，发出去的是裸 VLESS。
   判据只有一条：抓包看那条连接的首个上行。正常 TLS 是 1400~1500 字节的 ClientHello，
   降级的现实是 **289 字节**、服务端一个字都不回，error.log 里对得上一行
   `REALITY: processed invalid connection … failed to read client hello`。
   （`strings libgojni.so | grep -c reality` 返回值是 1，而且那是单词沙拉里的碎片。）
   所以内置核心能用的协议只有 v2ray v5 认识的那些：`vless+ws+tls`、`trojan`、
   `vmess`、`ss`。要上 reality 就得换 `AndroidLibXrayLite`，那是重写
   `ProxyCore` / `CoreController` / `measureOutboundDelay` 的量。
8. **单飞通道必须有优先级。** `SpiderClient.call` 只有一条串行锁加一个全局
   `GENERATION`，谁来都 `incrementAndGet()` —— 于是手指按下卡片触发的那次
   **详情预取**，能把用户正在等的分类翻页判成「被更新的请求取代」。表现是
   「滑得快就加载失败」。后台任务要么抢不到锁就放弃，要么不许作废前台请求；
   而 JS 侧收到「取代」这类取消，不该置错误态 —— 那会把「自己人掐掉的」说成故障。

### APK 自更新：GitHub Releases + 镜像（2026-10-17 改）

清单和包都在 `zhaoruizhe81/AIIvideo` 的 Releases 上，本地不存副本：

```text
https://github.com/zhaoruizhe81/AIIvideo/releases/latest/download/android-update.json
```

清单里的 `urls[]` 是一组下载地址（GitHub 原始 + gh-proxy + ghfast），
`UpdateMirror.pick()` 并发下每个源的前 256KB，按真实耗时挑最快的。
**不要退回 HEAD 探速**：GitHub 的 release asset 在边缘节点回 302 只要 30ms，
但实际下行被限得厉害，只探头会把最慢的那条选出来。

两个必踩的坑，都写进代码注释了：

- `HttpURLConnection.setInstanceFollowRedirects(true)` **只跟同主机**跳转。
  GitHub 会 302 到 `objects.githubusercontent.com`，gh 镜像 302 到自己的 CDN，
  自动重定向在这里不生效——拿到的是空 302 响应。`UpdateMirror.open()` 手动
  跟 `Location`，检查更新和下载都走它。
- 国内两个平台（Gitee / GitCode）都不能做匿名大文件直链：Gitee 的 raw 和发行版
  附件一律 403（2020 年后强制登录）；GitCode 的 raw 回「暂不支持预览」，
  uploads API 对 60MB 直接 413。这两个平台不要浪费时间。

下载本身在 `UpdateMirror.download()`（Java）：64KB buffer、边下边算 sha256、
进度用反射调回 `UpdateManager$Progress.onPercent`（那个接口在 smali 里，
Java 编译期看不到）。

**二、APK 自更新（2026-10-27 起恢复，现行）**

```text
Endpoints.UPDATE_MANIFEST
→ raw.githubusercontent.com/zhaoruizhe81/AIIvideo/main/android-update.json
→ 清单里的 urls[]：gh-proxy.com / ghfile.geekertao.top / gh.dpik.top / github.com
                   …/AIIvideo/releases/download/<tag>/AIIvideo-<tag>-release.apk
```

清单五步走完就发完了，`v2.0.26` 就是这么发的：

1. `work/android/app/build.gradle.kts` 提 `versionCode` / `versionName`；
2. `./scripts/build.sh verify`（清空重建 + 单测 + 断言 APK），产物在
   `app/build/outputs/apk/release/app-arm64-v8a-release.apk`；
3. 写仓根的 `android-update.json`：`versionName` / `versionCode` / `tag` / `apk` /
   `urls`（四条，第一条最前面是镜像）/ `sha256` / `size` / `notes`。
   **`sha256` 和 `size` 必须对着真包算一遍**，`UpdateMirror.download()` 是边下边算、
   对不上直接判失败；
4. `git push origin main` —— 清单就在 main 上，推上去 App 立刻能读到；
5. `gh release create vX.Y.Z --title "X.Y.Z —— 一句话" --notes-file 说明.md \

   **asset 名必须和清单里的 `apk` 字段逐字一致**，否则四条下载链接全 404。

顺序上 3/4 在 5 前面，中间有几十秒窗口：清单已指向一个还没建好的 release。App 只在
冷启动查一次、且有 12 小时节流，实际没影响；在意的话先发 release 再推清单。

`versionCode` 是 20000 + 小版本号（2.0.26 → 20026），App 比的是它，不是字符串。

## 品牌

应用名 **AIIvideo**，图标白底黑 A。改了三处：

| 位置 | 值 |
|---|---|
| `AndroidManifest.xml` `android:label` | `AIIvideo` |
| `assets/app.html` `<title>` | `AIIvideo` |
| `assets/app.js:118` `document.title` | `AIIvideo` |

图标走自适应图标（minSdk 26，正好是自适应图标的下限，所以不需要传统 PNG 分级）：

```text
res/mipmap-anydpi/ic_launcher.xml
  ├── background  @color/orange_icon_background   = #ffffff  （原版就是白的，没动）
  └── foreground  @drawable/orange_icon_foreground = 矢量图，居中一个黑色的 A
```

源文件在 [`work/shells/brand/aiivideo-icon.svg`](../work/shells/brand/aiivideo-icon.svg)，画布 108×108 与规范一致，同一套几何直接搬到 VectorDrawable。A 收在中心半径 34 以内，圆形/圆角方形/方形三种蒙版下都不会被裁。三段同色图形拼出字母（两条斜杠 + 一条梯形横杠），字腔和开裆都是"没画"画出来的。

**外圈形状由桌面的图标蒙版决定，图标本身管不了。** 小米桌面默认用圆角方形，所以装上去看到的是白色圆角方块；桌面设成圆形图标时，同一份资源就是白色圆 + 黑 A。如果想让圆是图标自己画出来的、不随桌面变，用 [`aiivideo-icon-circle.svg`](../work/shells/brand/aiivideo-icon-circle.svg)（圆径 66、A 缩放 0.80）——代价是圆以外透明，桌面底色会透出来。

**顺手清掉的老 logo 比改名本身值钱。** `res/drawable-nodpi/orange_logo.png` 是张 1254×1254 的 PNG，841694 字节，而 apktool 的 `doNotCompress` 名单里有 `png`，所以它是**原样压进 APK** 的。改矢量后它没人引用了，换成 1×1 透明图（保留 `public.xml` 的 id 与 `R$drawable` 字段，避免 apktool 重排资源 ID 把 smali 里的 R 常量对错位）。整包从 9064903 掉到 8098177 字节，小 966726，**10.7%**。

**包名没改。** 还是 `com.huangguo.mobile`，`FileProvider` 的 authority 也还是 `com.huangguo.mobile.updates`。改包名等于换一个应用：覆盖安装会失败、老用户得先卸载、签名校验链路要重走一遍，而且 smali 里所有 `Lcom/huangguo/mobile/...` 的类型引用都得跟着改。这是个独立决定，要做的话单独开一轮。

## 对外发帖（`帖子/`）

发在论坛上的稿子放在仓库根目录的 [`帖子/`](../帖子/)，不跟代码混在一起。

```text
帖子/帖子.md            正文（Markdown）
帖子/images/            配图原图，1080×2400 的手机截图
帖子/_pdf-style.html    PDF 导出用的样式表
帖子/*.pdf              导出的审核稿
```

**配图走 mjj 图床**，不塞进仓库：`i.mji.rip` 的直链，Chevereto 那套接口，脚本在
`~/.dsh/skills/mjj-image-host/`。上传前先压小 —— 手机截图原图 800KB 上下，
`sips -Z 720 -s formatOptions 82` 之后是 30~70KB，七张图从 2.9MB 掉到 310KB。
论坛帖子里贴的是图床链接，PDF 里那份是内嵌副本。

导 PDF：

```bash
cd 帖子
pandoc 帖子.md -f gfm -t html5 --standalone --include-in-header=_pdf-style.html -o /tmp/post.html
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --disable-gpu \
  --no-pdf-header-footer --virtual-time-budget=15000 --print-to-pdf=/tmp/post.pdf file:///tmp/post.html
```

不用 xelatex 那条路：中文得配 xeCJK 和字体，容易出豆腐块；Chrome 直接吃系统字体，
中英混排、远程图片外链都是稳的。`--virtual-time-budget` 要给够，不然图还没下完就打印了。

**论坛正文是 BBCode，不是 Markdown。** `[img]`、`[url]`、`[sell=0,money]`，
和 `帖子.md` 里的 `![]()` 是两套。改完帖子两边都要动，别只改一边。

发出去之前先在 Edit 页里核一遍：`[sell]` 有没有配对、`[img]` 数对不对、
有没有 Markdown 残留（`](http` 或行首 `#`）。
